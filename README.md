# Arc Tracker iOS prototype scaffold

STATUS: uncompiled prototype scaffold, NOT a working iPhone app. It has been
generated and rendered for inspection only. It has never been compiled into an
app binary (that needs macOS/Xcode), never installed on a device, and its
unlock/sync/photo features cannot reach the backend yet (see "Backend access"
below). Prepared Nov 20, 2026.

Built from the actual site source: github.com/drelly3/kaminari-site @ 096bd63,
generated with `node build.mjs` and copied from `dist/`. Nothing in the live
site, Worker, or member data was changed.

## What is in here

- `www/` - the tracker client exactly as the site builds it (`arc-tracker.js`,
  `arc-gate.js`, styles, icons), with the site's own `app.html` as `index.html`.
- `www/api-shim.js` - the only added code. The tracker calls its backend at
  `/api/...`; inside the shell those calls are redirected to
  `https://animemindset.com/api/...`. Remove this file (and its script tag in
  `index.html`) if the backend is reached differently.
- `capacitor.config.json` - app id `com.animemindset.arctracker` (change before
  real distribution), name "Arc Tracker".
- `ios/` - the Xcode project, generated by `npx cap add ios`. If it is missing
  (it is not committed to the git repo), regenerate with `npx cap add ios`
  followed by `npx cap sync ios`.

Note: the bundled gate runs in the repo's development preview mode (the "Skip
the key" button and the printed sample key are visible). The site's production
build forces this off; for the scaffold it is harmless and even handy for UI
testing, but it must be built off before any real distribution.

## Verified rendering (synthetic local test)

The bundled `www/` was served locally and rendered at iPhone size with every
`/api/*` call mocked, so the test made zero requests to the live backend. The
gate screen, the first-run intro, and the archetype picker all render correctly
from these exact files (screenshots delivered alongside this scaffold).

## Backend access (the open piece)

The Cloudflare Worker answers cross-origin requests with 405 and no allow
header (verified in source and live), so a native shell cannot call the API
yet. Three ways forward, in order of increasing footprint:

1. **Local mock (no server change at all)** - run the shell against mocked
   `/api/*` responses, exactly like the rendering test above. Validates UI,
   gate flow, offline behavior. Validates nothing about real sync.
2. **Isolated staging Worker** - deploy a second, separate Worker from the same
   code with CORS enabled and its own empty KV/R2 namespaces. Production and
   member data stay untouched; testers' real arcs are not involved. Setting
   this up is itself an action on the Cloudflare account and needs approval,
   but it modifies nothing that is live today.
3. **CORS allowlist on the live Worker** - one small change to `worker.js`
   allowing the shell's origin. This is the eventual shipping path, and also
   needs explicit approval. It is NOT required for the prototype phase if
   option 1 or 2 is used.

## Known gaps (deliberate)

1. **Reminders**: reminders use web push (service worker + VAPID), which does
   not work inside a native shell. Next iteration: schedule the habit reminders
   on the device with `@capacitor/local-notifications` (client-side, no backend
   change), or add native APNs later.
2. **Access key gate**: kept as-is. The first App Store version is planned
   free, so the key check behaves like a login. If paid access is added later,
   Apple guideline 3.1.1 requires in-app purchase for unlocking functionality -
   the Gumroad key check cannot be the paid unlock in an App Store build.
3. **App Store privacy**: a privacy policy URL and App Store privacy labels are
   required for any app, free or paid. The client uses no third-party SDKs
   (only Google Fonts), which keeps the label inventory small.

## Building it

Compiling any iOS app requires macOS. Andrel works on Windows, so the path is:

**Step 1 - automated compile check, $0, from Windows (prepared here).**
`.github/workflows/ios-build.yml` is a ready-to-commit GitHub Actions workflow
that compiles this scaffold on GitHub's hosted macOS runners and uploads the
built app as an artifact. It runs only when manually triggered. Standard
GitHub-hosted runners are free for public repositories (GitHub billing docs:
docs.github.com/en/billing/concepts/product-billing/github-actions), and the
kaminari-site repo is public, so this costs nothing and needs no new service
account. It goes in via a separate branch/PR in his own repo (his Claude Code
workflow can file it) - adding it is a write to his repo and needs his OK.
What it proves: the scaffold compiles into a real iOS app package (unsigned,
iOS Simulator target). What it does NOT do: put the app on his iPhone.

**Step 2 - on-device testing (later, needs one of two things).**
Installing on a physical iPhone requires signed provisioning:
- Borrowed/rented Mac: open `ios/App/App.xcodeproj` in Xcode, sign in with an
  Apple Account, run on his iPhone. A free Apple Account ("Personal Team") is
  enough for device testing through Xcode
  (developer.apple.com/support/compare-memberships/).
- Or the $99/year Apple Developer Program, which also unlocks TestFlight and
  App Store distribution. Cloud CI alone does NOT put the app on a phone:
  registering a device for provisioning requires the paid program.

Ionic Appflow is not recommended for new setups: Ionic announced a multi-year
wind-down (ionic.zendesk.com, Nov 2026).

## First on-device test checklist (once built and a backend path is chosen)

- Gate opens with a valid beta key.
- Progress saves and syncs; a second device restores it.
- Progress photos pick from camera/library and upload.
- App works offline and catches up when back online.
- Reminders: expected NOT to fire in this scaffold (see gap 1).
